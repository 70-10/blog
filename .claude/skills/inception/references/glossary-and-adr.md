# 用語集と ADR（Inception での扱い）

用語集は「語」を固定し、ADR は「判断」を固定する。どちらも 1 つの変更をまたいで残るリポジトリ共有の資産なので `docs/intents/<slug>/` の外に置く。

**書式・置き場・書くかどうかの判定は `${CLAUDE_PROJECT_DIR}/docs/recording-conventions.md` が定める。** ここには Inception 固有の点だけ書く。

| 記録 | 置き場 |
|---|---|
| 用語集 | `docs/glossary.md` |
| ADR | `docs/adr/0001-<slug>.md` |

## いつ書くか

2 つの入口がある。

**対話の最中に固まったとき** — その場で書く。後でまとめて書かない（まとめると失われ、後付けで歪む）。書くきっかけは [対話ガイド](dialogue-guide.md) の「確定したら即記録する」。

**各ステップ末の承認ゲート** — 書き漏らしをここで拾う。手順は SKILL.md の「承認ゲート」節。対話の最中に書けていれば候補は出ないことが多く、それが通常の結果。

## Inception で ADR が出やすいところ

**ステップ0（スコープの In / Out）** で「やらない」を明示的に決めたときが一番出やすい。やらないと決めた範囲は後から拾い直すコストが大きく、決めた理由を書いておかないと後で「なぜ入れなかったのか」が分からなくなる。

**ステップ4（Unit 分割）** も出やすい。Unit の境界は後段の Construction が前提にするので後戻りしにくく、切り方を変えれば別の分け方があったという形でトレードオフも揃いやすい。

**ステップ1（現状・制約）** で既存の制約への対処方針を決めたときも該当する。既存の作りに合わせるのか、あえて外れるのかは、コードを読んでも理由が分からない類の判断になる。

どちらも 3 条件（後戻りしにくい / 文脈なしでは驚く / 本物のトレードオフ）をすべて満たすときだけ書く。「決めたから書く」ではない。

## 発生元の書き方

ADR の `発生元:` 行には `docs/intents/<slug>/` の `<slug>` を書く。どの検討から出た判断かを辿れるようにするため。Inception と Construction で同じ slug を使うので、どちらで出た判断も同じ書き方になる。
