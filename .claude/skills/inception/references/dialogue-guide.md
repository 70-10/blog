# what/why の対話ガイド

Inception の質は「**what（何を作るか）と why（なぜ作るか）をどこまで引き出せるか**」で決まる。各ステップで成果物を埋める前に、次の型で what/why を引き出す。機械的に全部こなすのではなく状況に応じて使う。

自分で決めて自分で作る場合も同じ型を使う。頭の中で決まっているつもりの why を一度言葉にすると、スコープの取りこぼしや思い込みの制約が表に出る。

## 引き出し方の型

1. **既知と未確定を切り分ける**（聞く前に分ける）
   - `CLAUDE.md` / 既存コード / 既存の `docs/` から既に分かること（既知）と、未確定・根拠不明なこと（曖昧）を分ける。既知は聞かず、曖昧だけを詰める
   - why: 分かることまで聞くと答える側の負担が大きく、答えも表面的になる

2. **why → what の順**
   - まず「なぜ必要か／無いと何が困るか」、次に「では正確には何を達成すればよいか」
   - why: 目的が曖昧なまま what を決めると、後で「そもそも何のため？」に戻って手戻りする

3. **答えやすくする（たたき台を添える）**
   - 文脈があれば「自分はこう考えるが、どうか？」と案を添えて聞く。必須ではない
   - why: 白紙から答えるのは難しい。たたき台があれば「選ぶ / 直す / 反論する」で答えられる

4. **暗黙の前提・矛盾・曖昧語を表に出す**
   - 曖昧語は言い換えを 1 つに揃えて確認する（例「"記事" は投稿のことか、それとも表示上のカードのことか」）。矛盾はその場で指摘する（例「A と B の両立に C が要るが C 未定」）
   - why: 言葉のずれや隠れた矛盾は、後工程（テスト設計・実装）で表に出ると高くつく

5. **絞った点は納得まで詰める**
   - 詰めると決めた点は、未確定ゼロ、または「実装しないと分からない」と明示できるまで詰める。いま詰めない未確定は `questions.md` に残す
   - why: 中途半端に詰めて放置すると、後から同じ議論に戻る

6. **やりすぎない**
   - 影響の大きい順に絞る。論点が多いときは重要な数件に集中し、残りは `questions.md` へ
   - why: 「徹底的に」は「全部を等しく」ではない。重要な所に深く、が質と速度を両立する

7. **What/Why ガード（要求レベルを保つ）**
   - 入力が「要求 / 要件 / 仕様」のどの高さかを判定する。Inception で記録するのは原則 **要求**（US）。AC は「何を満たすか（**要件**）」までで、**仕様（どう作るか）には踏み込まない**
     - 要求: 「こうしたい・こうありたい」という希望（主語は読む人や書く人）。例「読んでいる記事のどこまで進んだか分かるようにしたい」
     - 要件: それを実現するため「何を実現するか」。例「記事の読み進み具合が画面上で分かる」
     - 仕様: 要件を満たす詳細な動作条件。例「画面上部に進捗バーを出す」
   - 仕様・実装に踏み込んでいるしるし: 主語が実装側（コンポーネント・CSS・ビルド）／ 実装語彙（＝どう作るかを表す語。コンポーネント名・クラス名・ファイル名など）が出る ／ why 抜きで「どう作るか」が先に来る
   - 見つけたら一旦立ち止まり、「**XXX ということなので、YYYY と直していいですか？**」と要求（AC では要件）レベルへの書き換えを提案する。承認されたらその高さで記録、**拒否されたらそのまま受け入れて進む**（気づいてもらうのが目的で、強制はしない）
   - why: 2 番（why → what）で why を先に置いても、what が無意識に仕様まで踏み込むことがある。要求のレベルを保つほど Construction での設計の自由度が残る。要件・仕様の議論自体を禁じるものではない（必要な場面はある）

## ステップ別に特に詰める点

| ステップ | 特に詰める what/why |
|---|---|
| 0 起点整理 | why 最優先。なぜこの変更が必要か／無いと何が困るか |
| 1 現状・制約 | 各制約の「なぜこの制約か（根拠）」。根拠を言えない制約は思い込みかもしれない |
| 2 ユーザーストーリー | 「なぜこのストーリーか／本当の目的は」。So that を形だけにしない。仕様（どう作るか）に踏み込んでいないか（7番） |
| 3 受け入れ条件(AC) | US 間の矛盾・曖昧語の検出。AC が曖昧だと完成判定がぶれる。実装語彙に踏み込んでいないか（7番） |
| 4 Unit 分割 | 「なぜこの切り方か」。分割の理由を言えないと依存と順序が崩れる |

## 確定したら即記録する（用語集・ADR・memory.md）

対話で語や判断が固まったら、その場で書く。後でまとめて書かない（まとめて書こうとすると忘れるし、後付けで歪む）。書式は `${CLAUDE_PROJECT_DIR}/docs/recording-conventions.md`、Inception 固有の点は [glossary-and-adr.md](glossary-and-adr.md)。

- **用語が確定した瞬間**: 4 番で曖昧語の言い換えを揃えて統一語が決まったら、`docs/glossary.md` にその場で追記する（別名は「避ける別名」へ）。既存の用語集と食い違う語が出たときも、止めて突き合わせて確定させる
- **後戻りしにくい判断が固まった瞬間**: 3 条件（後戻りしにくい / 文脈なしでは驚く / 本物のトレードオフ）を確かめ、すべて成立するときだけ ADR を 1 本書く
- **解釈・逸脱・トレードオフ・疑問が出た瞬間**: そのステップの `docs/intents/<slug>/memory/step<N>.md` に 1 行足す。ADR や用語集に上げるほどでない判断もここに残す。書くこと自体に承認は要らない

上の 3 つは書き漏らしても、各ステップ末の承認ゲート（SKILL.md の「承認ゲート」節）で候補として拾い直す。ゲートは取りこぼしの受け皿であって、その場で書かなくてよい理由にはならない。
