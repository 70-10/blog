## 未解決の疑問

### Q1: 下書きをどんな形でリポジトリに持つか

**性質**: 内部の作り。**Stage 2（design）で決められる。人の判断は要らない。**

[ADR 0003](../../../../../adr/0003-articles-stay-as-markdown-in-this-repository.md) と [0006](../../../../../adr/0006-build-our-own-admin-screen-for-writing.md) でリポジトリの中に持つことは決まっている。開いているのは形だけ。

選択肢は 2 つに分かれる。どちらを採るかで触るファイルが変わる（[design-decisions.md](design-decisions.md) の表）。

| 案                                                             | 効くところ                                                     | 引き受けるもの                                                                                                                   |
| -------------------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| posts コレクションの中に置き、フラグで絞り込む                 | `getPosts()` の 1 か所で 5 つの生成物すべてから外せる          | **スキーマの `title` / `publishDate` / `tags` の必須を外すことになり、緩和が既存 97 記事にも効く。** lefthook の校正の除外も要る |
| posts コレクションの外（別ディレクトリか別コレクション）に置く | 生成物に出る経路がそもそも無い。スキーマも校正の対象も触らない | 下書きから記事への移し替えを Unit 2 が書く。移し替えのときにファイルが動く                                                       |

[constraints.md](constraints.md) の「コレクションのスキーマが本文だけの下書きを拒む」が分かれ目。**この比較は explore の観測であって、選択は design が行う。**

### Q3: 画面のテストをどの環境で走らせるか

**性質**: 内部の作り。**Stage 3（test-design）で決められる。**

`vitest.config.ts` の `environment` は今 `node` の 1 つだけ。画面の描画を確かめるならブラウザ寄りの環境が要る。土台は [ADR 0008](../../../../../adr/0008-admin-runs-as-its-own-pages-project-behind-cloudflare-access.md) で決まったが、画面をどの枠組みで作るかは Stage 2（design）が決めるので、それを見てから決める（[test-strategy.md](test-strategy.md) の「新しく足すテスト」）。

## 解消済みの疑問

### この Unit で解いたもの

**Q2: 管理画面をどこで動かし、認証をどう作るか** → [ADR 0008](../../../../../adr/0008-admin-runs-as-its-own-pages-project-behind-cloudflare-access.md)

Stage 1 の途中で `[B]`（中断）にして人に返し、決まった。動かす場所・入口の守り方・リポジトリを書く資格情報の 3 つは独立に選べないので、まとめて 1 案として決めている。

| 軸                       | 決着                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| 動かす場所               | ブログとは**別の** Cloudflare Pages プロジェクト。サブドメインで開く。プレビューデプロイは止める |
| 「自分だけが入れる」作り | Cloudflare Access。アプリ側は Access が付ける JWT を検証する                                     |
| リポジトリの書き込み     | `70-10/blog` だけに絞った細かい権限のトークンを秘密の値として持ち、Contents API を叩く           |

この決定が受ける制約（JWT の検証のしかた、`*.pages.dev` の露出、無料の範囲など）は [constraints.md](constraints.md) の「管理画面の土台」にある。

**人がリポジトリの外で用意するもの**（AI にはできない。Stage 4 に入る前に要る）:

1. 管理画面用の Cloudflare Pages プロジェクトを作り、サブドメインを割り当てる
2. そのプロジェクトのプレビューデプロイを止める
3. Zero Trust を有効にし、Access アプリケーションを登録して `Emails` に自分のアドレスを指定する
4. `70-10/blog` だけに絞った細かい権限のトークンを作り（Contents: read and write）、Cloudflare の秘密の値に登録する
