# quick-draft — ユーザーストーリー

「誰が」はこのブログでは**書く人**（自分）に寄る。公開も In に入ったが、読む人にとっては既存の記事が増えるだけなので、読む人を主語にしたストーリーは立てていない。

下書きの置き場・持ち方は、ここでは名指ししない。ステップ 1 で分かった通りスキーマが `title` / `publishDate` / `tags` を必須にしているため実現の選択肢が複数あり、そこを決めるのは Construction の設計になる。

「下書き」は、まだ公開されていない書き途中のものを指す。「記事」は公開されているものを指す。

## US-01: PC がない場所で着想を下書きとして残す

- **As a** 書く人
- **I want to** PC が手元にないときでも、着想したその場で下書きとして書き残したい
- **So that** PC を開けるようになるまでの間に着想が失われないから
- **優先度**: Must
- **参照**: `00_intent.md` の課題 1、`01_current-and-constraints.md` の「今の執筆の入口」

### 受け入れ条件（AC）

**シナリオ: 正常系 - PC がない場所で本文を書いて残す**

- Given PC が手元になく、スマホだけがある
- When 着想を本文として書いて下書きとして残す
- Then その下書きは後から取り出せる状態で保存されている

**シナリオ: 正常系 - タイトルが決まっていない**

- Given 何というタイトルにするか決まっていない
- When 本文だけを書いて下書きとして残す
- Then タイトル・タグを決めなくても保存できる

**シナリオ: 正常系 - タイトル先行**

- Given 本文はまだなく、タイトルだけ思いついている
- When タイトルだけを書いて下書きとして残す
- Then 本文が空でも保存できる

**シナリオ: 異常系 - 中身が空**

- Given 本文もタイトルも何も書いていない
- When 下書きとして残そうとする
- Then 下書きは作られず、残すものがないことが分かる

**シナリオ: ビルドと生成物 - 下書きは生成物に出ない**

- Given 下書きが残っている
- When サイトをビルドする
- Then ビルドは成功する
- Then 下書きは記事ページ・一覧・タグページ・RSS・OGP 画像のいずれにも現れない

**シナリオ: 既存コンテンツへの影響 - 既存記事が変わらない**

- Given 既存の 97 記事がある
- When 下書きを残す
- Then 既存記事の URL・日付・一覧の並び順は変わらない

**観点のスキップ**: 「表示」と「共有・SEO」は該当しない。下書きは公開されないため、読む人に見える表示も共有時の見え方も存在しない（上の「ビルドと生成物」で生成物に出ないことを確認済み）。

## US-02: 残した下書きをそのまま記事に書き継ぐ

- **As a** 書く人
- **I want to** 残した下書きを、書き直しなしでそのまま記事として書き継ぎたい
- **So that** 下書きが記事になる途中で作り直しが発生せず、着想から公開までが途切れないから
- **優先度**: Must
- **参照**: `00_intent.md` の完了の定義 2、`questions.md`（「そのまま記事に育てる」）

### 受け入れ条件（AC）

**シナリオ: 正常系 - 下書きの中身が引き継がれる**

- Given PC がない場所で残した下書きがある
- When その下書きを開いて書き継ぐ
- Then 残したときの本文がそのまま入っている
- Then 内容を写し直す・作り直す操作は要らない

**シナリオ: 正常系 - 足りない項目を後から与える**

- Given タイトル・タグが決まっていない下書きがある
- When タイトルとタグを与える
- Then 公開できる状態になる

**シナリオ: 異常系 - 校正に反する記述を含む下書きを書き継ぐ**

- Given 校正（textlint のルール）に反する記述を含む下書きがある
- When その下書きを開いて書き継ぐ
- Then 書いた通りの本文が引き継がれ、勝手に直されてはいない（校正は公開のときに働く。US-05 の異常系を参照）

**シナリオ: ビルドと生成物 - 記事になれば生成物に出る**

- Given 下書きを記事にした
- When サイトをビルドする
- Then その記事の記事ページ・一覧への掲載・タグページ・RSS・OGP 画像が生成される

**シナリオ: 表示 - 極端な中身でも崩れない**

- Given 長いタイトル、あるいはタグが多い記事がある
- When 記事ページと一覧を見る
- Then 既存記事と同じように崩れずに表示される

**シナリオ: 共有・SEO - description が未設定でも公開できる**

- Given `description` を設定していない記事がある（既存 97 記事のうち 86 記事が未設定）
- When 公開する
- Then 公開でき、共有時の見え方は既存の未設定記事と同じになる

**シナリオ: 既存コンテンツへの影響 - 既存記事が変わらない**

- Given 既存の 97 記事がある
- When 下書きから新しい記事を作る
- Then 既存記事の URL・日付・一覧の並び順は変わらない

## US-03: PC でも少ない手数で書き始める

- **As a** 書く人
- **I want to** PC で新しく記事を書き始めるときも、今より少ない手数で始めたい
- **So that** 書くこと以外の準備で気持ちが削がれないから
- **優先度**: Should
- **参照**: `00_intent.md` の課題 2、`01_current-and-constraints.md` の「今の執筆の入口」

「手数」は、本文に最初の一文字を打てるようになるまでに書く人が起こす操作の数で数える。今の手数は 4（ターミナルを開く → リポジトリへ移動 → `git pull` → `pnpm create-post`）。

### 受け入れ条件（AC）

**シナリオ: 正常系 - 今より少ない手数で本文に手をつけられる**

- Given PC の前にいて、新しく記事を書き始めたい
- When 新しい入口を使う
- Then 本文に最初の一文字を打てるまでの操作の数が 4 未満である

**シナリオ: 正常系 - 既存の入口がそのまま動く**

- Given `pnpm create-post` を使いたい
- When 実行する
- Then 今と同じようにタイトル・slug・タグを聞き、記事のファイルを作る

**シナリオ: 既存コンテンツへの影響 - 既存記事が変わらない**

- Given 既存の 97 記事がある
- When 新しい入口を足す
- Then 既存記事の URL・日付・一覧の並び順は変わらない

**観点のスキップ**: 「異常系（データの不備）」「ビルドと生成物」「表示」「共有・SEO」は該当しない。このストーリーは書き始める操作だけを対象にし、記事の中身も生成物も変えないため。

## US-04: 溜まった下書きを見返して整理する

- **As a** 書く人
- **I want to** 残してある下書きを見返して、まとめるもの・捨てるものを判断したい
- **So that** 似た着想が散らばったまま溜まらず、次に書くものを選べるから
- **優先度**: Should
- **参照**: ステップ 2 の対話（見返して統合・不要の判断をする）

### 受け入れ条件（AC）

**シナリオ: 正常系 - どんな下書きがあるか分かる**

- Given 下書きが複数残っている
- When 下書きを見返す
- Then 残っている下書きが一覧で分かる
- Then それぞれ何について書いたものか見分けられる

**シナリオ: 正常系 - 同じ内容の下書きをまとめる**

- Given 同じことを書いた下書きが 2 つある
- When 1 つにまとめる
- Then まとめた結果が下書きとして残り、元の 2 つは残らない

**シナリオ: 正常系 - いらない下書きを捨てる**

- Given もう書くつもりのない下書きがある
- When 捨てる
- Then その下書きは一覧に出なくなる

**シナリオ: 異常系 - 下書きが 1 件もない**

- Given 下書きが 1 件も残っていない
- When 下書きを見返す
- Then 1 件もないことが分かる（エラーにはならない）

**シナリオ: 表示 - 見分けにくい下書きが混ざる**

- Given タイトルが決まっていない下書きと、決まっている下書きが混ざっている
- When 一覧を見る
- Then タイトルが決まっていない下書きも何について書いたものか見分けられる

**シナリオ: ビルドと生成物 - 下書きの増減はサイトに影響しない**

- Given 下書きをまとめたり捨てたりした
- When サイトをビルドする
- Then ビルドは成功し、生成物は下書きの増減の前後で変わらない

**観点のスキップ**: 「既存コンテンツへの影響」「共有・SEO」は該当しない。下書きの整理は公開された記事に触らないため。

## US-05: PC がない場所から記事を公開する

- **As a** 書く人
- **I want to** PC が手元にないときでも、書き上げた記事を公開したい
- **So that** 手元で整えるところまで進めても最後の一歩で止まる、ということがなくなるから
- **優先度**: Must
- **参照**: `00_intent.md` の課題 3、`docs/adr/0004-treat-idea-to-publish-as-one-change.md`

公開のために必要になる既存の修正も含める。ステップ 1 で「下書きだから不要」と決着させた 2 点は、公開まで含めたことで決め直した（`questions.md`）。

### 受け入れ条件（AC）

**シナリオ: 正常系 - PC がない場所から公開する**

- Given PC が手元になく、公開できる状態の下書きがある
- When 公開する
- Then サイトに記事が出る（記事ページ・一覧・タグページ・RSS・OGP 画像に反映される）

**シナリオ: 正常系 - 記事の日付は公開した日になる**

- Given 過去に残した下書きがある
- When 公開する
- Then その記事の日付は、下書きを残した日ではなく公開した日になる
- Then 一覧の並び順もその日付で決まる

**シナリオ: 正常系 - 公開前に記事ページの見え方を確認する**

- Given 公開しようとしている記事がある
- When 公開前に出来ばえを確認する
- Then 記事ページで、タイトルがどれくらいの長さに見えるかが分かる
- Then 本文がどう見えるか、どこで改行が入るかが分かる
- Then 画像を使っている場合は、画像の見え方も分かる

**シナリオ: 正常系 - 公開前にトップページでの見え方を確認する**

- Given 公開しようとしている記事がある
- When 公開前に出来ばえを確認する
- Then トップページの一覧で、タイトルがどれくらいの長さに見えるかが分かる

**シナリオ: 共有・SEO - 公開前に OGP 画像を確認する（Should）**

- Given タイトルの長い記事を公開しようとしている
- When 公開前に OGP 画像を確認する
- Then タイトルの長さによって見た目が崩れていないかが分かる

このシナリオだけ Should。上の 2 つ（記事ページ・トップページ）は Must。

**確認対象に含めないもの**: 記事の日付。確認の時点ではまだ公開していないため日付は決まらないが、確認時に注視する箇所ではないため問わない。タグページと RSS も公開前の確認対象には入れない。

**シナリオ: 異常系 - 校正の指摘がある**

- Given 校正（textlint のルール）に反する記述が本文にある
- When 公開しようとする
- Then 公開されない
- Then どこが指摘されたか分かる
- Then 本文は自動で書き換わらない

**シナリオ: 異常系 - 記事に必要な項目が足りない**

- Given タイトルまたはタグが決まっていない
- When 公開しようとする
- Then 公開されず、足りない項目が分かる

**シナリオ: 異常系 - 間違って公開したものを取り消す**

- Given 間違って公開してしまった記事がある
- When PC がない場所から取り消す
- Then その記事は記事ページ・一覧・タグページ・RSS から出なくなる

**シナリオ: ビルドと生成物 - 公開でビルドが通る**

- Given 公開できる状態の記事がある
- When 公開する
- Then ビルドが成功し、OGP 画像が生成される

**シナリオ: 表示 - 極端な中身でも崩れない**

- Given 長いタイトル、あるいはタグが多い記事を公開した
- When 記事ページ・一覧・タグページを見る
- Then 既存記事と同じように崩れずに表示される

**シナリオ: 共有・SEO - 共有時の見え方が意図どおり**

- Given 公開した記事がある
- When 共有時の見え方を確かめる
- Then タイトル・`description`・OGP 画像・canonical が既存記事と同じ規則で入る

**シナリオ: 既存コンテンツへの影響 - 既存記事が変わらない**

- Given 既存の 97 記事がある
- When 新しい記事を公開する
- Then 既存記事の URL・日付・一覧の並び順は変わらない
