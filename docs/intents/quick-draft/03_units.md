# Unit 分割 — quick-draft

US・AC を 6 つの責務に分解してから束ねた。責務の一覧と束ね方の理由は `memory/step4.md` にある。

実現の方法は [ADR 0006](../../adr/0006-build-our-own-admin-screen-for-writing.md) で決めた。**記事を書く画面を自分で作り、公開までその中で完結させる。** 下書きはリポジトリの中に持ち、画面の裏側が読み書きする。各 Unit の中身はこの決定を前提にしている。

## 作るものの割り振り

ADR 0006 で引き受けた 8 つを、どの Unit で作るかを先に示す。Unit ごとの詳細は下の一覧にある。

| 作るもの                                 | Unit   |
| ---------------------------------------- | ------ |
| 認証（自分だけが入れる）                 | Unit 1 |
| リポジトリを読み書きする裏側             | Unit 1 |
| 編集画面（自動保存）                     | Unit 1 |
| 下書きの保存の形（公開されない）         | Unit 1 |
| 最小の一覧（書きかけを開き直す）         | Unit 1 |
| 校正を実行する場所                       | Unit 2 |
| 公開と取り消し                           | Unit 2 |
| プレビューの描画                         | Unit 3 |
| 一覧（冒頭の抜粋つき）・まとめる・捨てる | Unit 4 |

**Unit 1 に 5 つが集中する。** 画面の土台・認証・公開 URL へのデプロイ・読み書き・エディタが一度に乗るので、4 つのうち一番重い。それでも割らないのは、割ると「ログインできるが何もできない画面」という単独では価値の出ない Unit ができるため。

## Unit 一覧

### Unit 1: 下書きを残せるようにする（slug: draft-anywhere）

- **概要**: 管理画面を立ち上げ、そこから下書きを書いて残せるようにする。画面は公開 URL で開けて自分だけが入れる。下書きは必須項目（タイトル・タグ・日付）が決まっていなくても持てて、サイトの生成物には現れない。書きかけを開き直せる最小の一覧まで含む
- **含む US**: US-01, US-03
- **この単位にした理由**: 「下書きを保存できて公開されない」と「そこへ書き入れる」は分けても片方だけでは価値が出ない。画面から書くと決めたので、画面の土台と認証もここに乗る。以降のすべての Unit がこの Unit を前提にする
- **完了の目安**: PC が手元にない状態で管理画面を開き、自分だけが入れて、着想を下書きとして残せる。本文だけ・タイトルだけでも残せる。両方空なら作られない。残した下書きを開き直せる。下書きがある状態でビルドが通り、記事ページ・一覧・タグページ・RSS・OGP 画像のどこにも下書きが出ない。`pnpm create-post` は今と同じように動く

### Unit 2: 下書きを記事にして公開する（slug: publish-from-draft）

- **概要**: 画面から下書きを書き継いで記事に変え、そのまま公開する。公開したものを取り消せる。校正を実行する場所もここで作る
- **含む US**: US-02、US-05（公開前確認の 3 シナリオを除く）
- **この単位にした理由**: 「記事に変える」と「公開する / 取り消す」は対になるひと続きの振る舞い。書き継ぎ（US-02）は記事に変える手前の段で、同じ責務に含まれる。校正は公開を止める門番なので、公開と同じ Unit に置く
- **完了の目安**: 下書きの本文が写し直しなしで引き継がれる。タイトルとタグを与えれば画面から公開でき、足りなければ止まって何が足りないか分かる。記事の日付は公開した日になる。校正（textlint のルール）の指摘があれば公開されず、どこが指摘されたか分かり、本文は自動で書き換わらない。公開したものを PC がない場所から取り消せる。既存の 97 記事の URL・日付・並び順が変わらない

US-05 の受け入れ条件のうち、この Unit に入るのは次のシナリオ。

- 正常系 - PC がない場所から公開する
- 正常系 - 記事の日付は公開した日になる
- 異常系 - 校正の指摘がある
- 異常系 - 記事に必要な項目が足りない
- 異常系 - 間違って公開したものを取り消す
- ビルドと生成物 - 公開でビルドが通る
- 表示 - 極端な中身でも崩れない
- 共有・SEO - 共有時の見え方が意図どおり
- 既存コンテンツへの影響 - 既存記事が変わらない

**校正について**: `textlint --fix` は残ったエラーの種類によって exit code が変わり、`--fix` 付きの実行は必ずしも止まらない（`questions.md` に記録）。公開を止めるには `--fix` なしで検査する経路が要る。

### Unit 3: 公開前に出来ばえを確認する（slug: preview-before-publish）

- **概要**: 公開する前に、公開後と同じ見た目を画面の中で見られるようにする
- **含む US**: US-05（公開前確認の 3 シナリオ）
- **この単位にした理由**: 本番と同じ見た目を出す仕組みは、公開する仕組みとは別の責務。**画面の中のプレビューは Astro のビルド結果とは別物になる**ので、「公開後と同じ見え方」をどう保証するかがこの Unit の設計課題になる。ここで詰まっても Unit 2 までは動く
- **完了の目安**: 記事ページでタイトルがどれくらいの長さに見えるか、本文がどう見えてどこで改行が入るか、画像を使っている場合は画像の見え方が、公開前に分かる。トップページの一覧でタイトルがどれくらいの長さに見えるかも分かる（ここまで Must）。タイトルの長い記事で OGP 画像が崩れていないかも分かる（Should）

記事の日付・タグページ・RSS は確認対象に入れない（`02_user-stories.md` の「確認対象に含めないもの」）。

### Unit 4: 溜まった下書きを見返して整理する（slug: organize-drafts）

- **概要**: Unit 1 の最小の一覧を、見返して判断できる一覧に育てる。本文の冒頭が出て、まとめる・捨てるができる
- **含む US**: US-04
- **この単位にした理由**: 「開き直すための一覧」と「見返して判断するための一覧」は求めるものが違う。前者は Unit 1 が要るぶんだけ持ち、後者はここで足す
- **完了の目安**: 残っている下書きが一覧で分かり、それぞれ何について書いたものか見分けられる。タイトルが決まっていない下書きも本文の冒頭で見分けられる。同じことを書いた 2 つを 1 つにまとめられ、元の 2 つは残らない。いらない下書きを捨てると一覧から消える。下書きが 1 件もなくてもエラーにならない。下書きの増減の前後で生成物が変わらない

## 依存関係

```
Unit 1（下書きを残せるようにする）
  → Unit 2（下書きを記事にして公開する）
      → Unit 3（公開前に出来ばえを確認する）
  → Unit 4（溜まった下書きを見返して整理する）
```

- **Unit 1 → Unit 2**: 下書きと、それを読み書きする裏側が無ければ記事に変えられない
- **Unit 2 → Unit 3**: 下書きを記事の形に写す決まりが無いと、公開後と同じ見た目を出せない
- **Unit 1 → Unit 4**: 最小の一覧が無ければ育てる対象が無い

**並行して作れる Unit は無い。** どの Unit も同じ管理画面と同じ裏側を触るので、並行させると同じファイルを二方向から変えることになる。作る順序は Unit 1 → Unit 2 → Unit 3 → Unit 4。Unit 4 は Unit 2・3 より先に回してもよいが、同時には回さない。

## US の割り振り

| US    | Unit                                             | 優先度 |
| ----- | ------------------------------------------------ | ------ |
| US-01 | Unit 1                                           | Must   |
| US-02 | Unit 2                                           | Must   |
| US-03 | Unit 1                                           | Should |
| US-04 | Unit 4                                           | Should |
| US-05 | Unit 2（公開前確認を除く）+ Unit 3（公開前確認） | Must   |

**US-05 だけ 2 つの Unit に跨る。** Unit 2 が終わった時点で US-05 の受け入れ条件は全部埋まらない（公開前確認が Unit 3 に残る）。US-05 が満たされるのは Unit 3 完了時点。

## 分割しなかった案とその理由

- **Unit 1 から土台と認証を切り出す案（5 Unit）** — Unit 1 は 8 つのうち 5 つを抱えて一番重い。それでも割らないのは、切り出した側が「ログインできるが何もできない画面」になり、単独では価値が出ないため。認証とデプロイを先に通せる利点はあるが、重さだけを理由に価値の出ない Unit を作らない
- **公開と公開前確認を 1 つの Unit にする案（3 Unit）** — 公開前確認は US-05 の Must なので、この案なら「Must が揃わないまま公開が動く期間」を通らない。採らなかったのは、その Unit の受け入れ条件が 12 シナリオを超えて Construction 1 回として重いため。取り消しは Unit 2 に入っているので、確認なしで出しても戻せる
- **技術レイヤー（下書きの保存 / 表示 / 公開）で切る案** — どの Unit も単独ではビルドが通っても価値が出ないため
- **US-03（PC でも少ない手数）を独立した Unit にする案** — 端末を問わない入口ができれば PC からも同じ入口を使えるので、分ける理由がない
- **全部を 1 つの Unit にする案** — Construction 1 回で回せる量を超える
