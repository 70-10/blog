# quick-draft — 確認した Q&A と未解決

## 解決済み

- [Q] スマホだけでどこまでできるようにしたいか
- [A] 公開まではしなくてよい。着想したときに短い下書きでも書けるようにしたい（step0）

- [Q] 記事の正の置き場をこのリポジトリの Markdown のままにするか
- [A] 変えない。過去に Contentful を使っていたが管理のしづらさで手放した経緯がある（step0 → `docs/adr/0003`）

- [Q] スマホで残した下書きはその後どう使うか
- [A] そのまま記事に育てる。着想を書き留めただけの下書きで止めない（step0）

- [Q] 公開の操作を今回のスコープに入れるか
- [A] step0 ではスコープ外で確定したが、step2 のゲートで撤回し In に戻した。理由は「下書きを整えられても公開できないと記事にならない」。公開のために必要になる既存の修正も含める（step2 / US-05）

- [Q] 公開の仕組み（`getPosts()` の絞り込みなど既存コード）に手を入れてよいか
- [A] Construction で得失を見て決める。Inception では禁じも許可もしない（step2）

- [Q] `pnpm create-post` をどう扱うか
- [A] 廃止・作り直しはしない。目的は入口を増やすこと（step0）

- [Q] スマホで撮った画像を下書きに含められる必要があるか
- [A] 今回は不要。スコープ外（step1）

- [Q] 下書きの段階でタイトル・タグを決める必要があるか
- [A] タイトルは決められてもよいが必須にはしない。ほとんどの場合は本文を書いてから最後にタイトルを決めるが、タイトル先行のこともたまにある。タグは下書きの段階では決めない（step1）

- [Q] 校正（textlint）をどの時点で通すか
- [A] 下書きの段階では通さない（step1）。ただし公開を In に戻したため、公開される記事をどこで通すかは決めが要る（step2 → step3 の AC で決める）

- [Q] 下書きが増えたときに見返す必要があるか
- [A] ある。見返して「これとこれは同じことを書いている」とまとめたり、「この記事はいらない」と捨てたりする判断をする（step2 → US-04）

- [Q] PC 側の入口（今より少ない手数で書き始められる）も今回作るか
- [A] 作る。In のまま（step2 → US-03）

- [Q] 公開される記事の日付を、下書きを作った日とするか公開した日とするか
- [A] 公開した日（step3 → US-05 の AC）

- [Q] スマホから公開するとき校正（textlint）をどう扱うか
- [A] 指摘があれば公開を止める。自動修正はしない（step3 → US-05 の AC）

- [Q] 公開前に出来ばえを確認する必要があるか、どこまで確認するか
- [A] 確認は絶対にしたい。対象は「記事ページでのタイトルの見え方」「本文の見え方と改行位置」「画像を使っている場合の画像」「トップページの一覧でのタイトルの見え方」で、ここは Must。OGP 画像はタイトルの長さで崩れるので確認できると嬉しい（Should）。タグページと RSS は対象外（step3 → US-05 の AC）

- [Q] 「日付は公開した日になる」と「公開前に公開後と同じ見た目を見られる」が両立しないのをどう解消するか
- [A] 日付は確認対象に含めない。確認時に注視する箇所ではないため問わない（step3 → US-05 の AC）

- [Q] 本文もタイトルも空の下書きを作れるようにするか
- [A] どちらも空なら作らない。どちらか一方でもあれば作る（step3 → US-01 の AC）

- [Q] 間違って公開したときにスマホから取り消す必要があるか
- [A] 必要（step3 → US-05 の AC）

- [Q] スマホからの入口と下書きの置き場をどうするか
- [A] 自作の管理画面を作る（案 B）。公開・取り消し・公開前の確認も画面の中で完結させる。GitHub をそのまま使う案は書く道具として馴染まないため、外部のメモアプリ案はリポジトリから遠く管理しづらいため却下（→ `docs/adr/0006`）

- [Q] `worktree-admin` / PR #904（tools/admin の骨組み）をどうするか
- [A] 完全に捨てる。PR はクローズ済み、worktree とローカルブランチは削除済み。`origin/worktree-admin` は参照用に残す

- [Q] `draft-command` ブランチ（/draft コマンドと文体ガイド）をどうするか
- [A] 丸ごと捨てる（削除は未実施）

- [Q] Cloudflare Pages に `main` 以外のブランチのプレビューデプロイが設定されているか
- [A] 有効になっている。PR #904（`worktree-admin`）と PR #917（`renovate/astro`）の Cloudflare ボットのコメントに `Branch Preview URL: https://<branch>.blog-68b.pages.dev` がある。ただし決定 2 で画面の中のプレビューを採ったため、Unit 3 では直接は使わない

## 未解決

- [Q] 公開の経路をどう作るか。校正の AC（指摘があれば公開を止める）により、`main` への素の push では成立しない。textlint は今 lefthook の pre-commit でしか走らず、CI は `pull_request` でしか動かないため（step3 → **Unit 2 `publish-from-draft`** で解く）
  - 追加で分かったこと: **`textlint --fix` は残ったエラーの種類によって exit code が変わる。** 検証用の記事（`sentence-length` と `ja-no-weak-phrase` が残存）では exit 0、`docs/recording-conventions.md`（7 件残存）では exit 1 だった。つまり `--fix` 付きの実行は「必ず止める門番」にならない。公開を止めるには `--fix` なしで検査する経路が要る
- [Q] 下書きをどこにどう持つか。**リポジトリの中に持つことは決まった**（ADR 0006）が、形は開いている。`src/content/posts/` は使えない（`getPosts()` が絞り込まないので公開される、かつスキーマが `title` / `publishDate` / `tags` を必須にするので本文だけの下書きはビルドを落とす）。別ディレクトリか、フラグと絞り込みかは未定（step1 / step2 → **Unit 1 `draft-anywhere`** で解く）
- [Q] 管理画面をどこで動かし、認証をどう作るか。ADR 0006 で自作すると決めたが、技術構成は決定 1 で白紙に戻した（step2 → **Unit 1 `draft-anywhere`** で解く）
- [Q] 画面の中のプレビューを、本番の Astro のビルド結果とどう一致させるか。受け入れ条件は「公開後と同じ見え方」だが、自作の描画は別物になる（step3 / ADR 0006 → **Unit 3 `preview-before-publish`** で解く）
- [Q] Cloudflare Pages のブランチプレビュー URL は、ブランチ名の `/` を `-` に置き換える（`renovate/astro` → `renovate-astro.blog-68b.pages.dev` で確認）。スラッシュ 2 つの `intent/<intent>/unit/<unit>` でも同じ規則かは未確認。最初の PR で実物を見れば分かる（決定 5）
