# 管理画面は独立した Pages プロジェクトに置き、入口は Cloudflare Access で守る

Status: accepted
発生元: quick-draft

[ADR 0006](0006-build-our-own-admin-screen-for-writing.md) で自作すると決めた管理画面の技術構成を決める。
動かす場所・入口の守り方・リポジトリを書く資格情報の 3 つは独立に選べないので、まとめて 1 つの案として選んだ。
ブログとは別の Cloudflare Pages プロジェクトを作り、サブドメインで開く。入口は Cloudflare Access が守り、
アプリ側は Access が付ける JWT を検証するだけにする。リポジトリへの書き込みは、`70-10/blog` だけに絞った
細かい権限のトークンをサーバー側の秘密の値として持ち、そこから Contents API を叩く。
別プロジェクトにするのは、ブログのビルドとデプロイから切り離せることと、管理画面側のプレビューデプロイを
止めて `*.pages.dev` の露出を 1 か所に閉じ込められるため。Access を選ぶのは、入口を守る責任がリクエストの
届く前にあり、自分で書く認証のコードが JWT の検証だけで済むため。

却下した代替案: ブログと同じ Pages プロジェクトのパス配下（`blog.70-10.net/admin`）に置く — 用意するものが
最少で、新しいプロジェクトも DNS レコードも要らない。それでも採らないのは、管理画面がブログと同じビルドと
同じデプロイに乗り、ブランチプレビューを push するたびに `<branch>.blog-68b.pages.dev/admin` にも出てしまうため。

却下した代替案: GitHub App のユーザー認証（sign in with GitHub）で自分を認証する — 管理する画面が増えず、
リポジトリを書く権限がログインした本人と一致する。それでも採らないのは、ログインの往復・ログイン状態の保持・
失効の扱いを自分で書いて保守することになり、入口を守る責任が自分のコードに乗るため。

却下した代替案: 画面に入口の制限を持たせず、端末に保存したトークンで直接書く — 用意するものが最少。
それでも採らないのは、[03_units.md](../intents/quick-draft/03_units.md) の Unit 1 の完了の目安
「自分だけが入れて」を満たさないため。

却下した代替案: リポジトリの書き込みを GitHub App のインストールトークンで行う — 長命の資格情報を持たずに済む。
それでも採らないのは、秘密鍵で JWT を作りインストールトークンを取る往復を実装することになり、1 人で使う
管理画面に対して割に合わないため。公開 URL と認証方式を変えずにあとから入れ替えられるので、先に簡単なほうを採る。
