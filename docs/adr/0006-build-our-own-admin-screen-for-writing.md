# 記事を書く画面を自分で作り、公開までその中で完結させる

Status: accepted
発生元: quick-draft

どこからでも下書きを書いて公開するために、GitHub の web / アプリでファイルを直接さわる案、
普段のメモアプリに下書きを置く案、自作の管理画面を作る案の 3 つを、5 つの場面ごとの操作で比べた。
自作の管理画面を採る。公開・取り消し・公開前の確認も画面の中で完結させ、外の画面へ移らない。
書く道具を自分で決められるのはこの案だけで、書く場所をリポジトリの近くに置いたまま保てるため。
引き受けるのは、認証・リポジトリの読み書き・下書き一覧・編集・まとめると捨てる・プレビュー・
校正の実行環境・公開と取り消しの 8 つを自分で作ること。とくに画面の中のプレビューは Astro の
ビルド結果とは別物になるので、「公開後と同じ見え方」をどう保証するかが設計課題として残る。

却下した代替案: GitHub の web / アプリをそのまま使う — 作る量が最小で、ブランチプレビュー・CI・PR
がそのまま使えて公開前の確認も本番と一致する。それでも採らないのは、記事を書くたびに GitHub の画面を
操作することになり、書く道具として馴染まないため。

却下した代替案: 普段のメモアプリに下書きを置く — 書き始めと整理が 3 案で最短。それでも採らないのは、
下書きがリポジトリから遠くなって管理しづらく、「書き直しなしでそのまま記事に育てる」ために取り込みの
自動化が必須になるため。
