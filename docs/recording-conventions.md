# 記録の書式

AI-DLC の Inception / Construction で残す 3 つの記録の書式を定める。両フェーズのスキルはここを参照する。書式をスキル側の references に書き写さない（片方だけ直って食い違うため）。

| 記録      | 何を固定するか         | 置き場                         | 寿命                 |
| --------- | ---------------------- | ------------------------------ | -------------------- |
| memory.md | 実行中の判断           | そのステージの作業ディレクトリ | そのステージ限り     |
| ADR       | 後戻りしにくい設計判断 | `docs/adr/`                    | リポジトリ共有・永続 |
| 用語集    | 語                     | `docs/glossary.md`             | リポジトリ共有・永続 |

どれも承認ゲートで振り分ける。振り分けの手順は下の「承認ゲートでの振り分け」にあり、各スキルの `## 承認ゲート` はそこを参照する。

## 承認ゲートでの振り分け

Inception の各ステップ末と Construction の各ステージ末にある承認ゲートで、次の 4 つをこの順に行う。Inception 5 ゲート・Construction 7 ゲート（implement は実装計画と完了の 2 回）の計 12 ゲートすべてで同じ。

このページと各スキルに出てくるコマンドとパスは、**リポジトリルートで実行する**前提で書いてある。別のディレクトリから実行すると解決できない。

### 1. learn 候補

```bash
bash .claude/scripts/memory-candidates.sh <このステージの memory.md のパス>
```

memory.md はステージごとに 1 ファイルなので、ステージを指定する引数は要らない。渡したファイルの中身がそのままそのステージの候補になる。

出た候補を一覧で見せ、AskUserQuestion で振り分ける（複数まとめて 1 問でよい）。

| 選択           | 動作                                                         |
| -------------- | ------------------------------------------------------------ |
| ルールに上げる | `docs/rules/` の該当ファイルに書く。memory.md の該当行は残す |
| memory に残す  | memory.md に残す                                             |
| 捨てる         | memory.md の該当行を消す                                     |

#### ルールの置き場

昇格先はフェーズで分ける。ファイル名がスコープを表し、ファイルの中に scope の欄は持たない。

| ファイル                     | 何を置くか                                   |
| ---------------------------- | -------------------------------------------- |
| `docs/rules/project.md`      | フェーズによらない、このリポジトリ全体の実践 |
| `docs/rules/inception.md`    | Inception の各ステップに効くもの             |
| `docs/rules/construction.md` | Construction の各ステージに効くもの          |

**既定は `project.md`。** そのフェーズでしか効かないと判断したものだけフェーズファイルへ置く。狭いほうを既定にするのは、1 回の作業で出た気づきがリポジトリ全体の決まりになってしまうのを防ぐため。

書き出す形は各ファイルの既存の書き方に合わせ、話題ごとの見出しの下へ箇条書きで足す。**近いテーマの記述が既にあるなら新しい見出しを作らずそこへ追記する。**

`docs/rules/` は**スキルが起動時に読む**。`inception` は `project.md` と `inception.md` を、Construction の各ステージは `project.md` と `construction.md` を読む。このリポジトリには `.claude/rules/` を自動で読み込む仕組みが無いため、読むことをスキル側の手順に入れている。

裏を返すと、**`docs/rules/` は AI-DLC を回しているときにしか効かない。** 記事を書く・依存を上げるといった普通の作業では読まれない。常に効かせたいものは `CLAUDE.md` に直接書く。

ルールに書いたものが効くのは**次回のスキル起動から**。実行中のステージには遡って効かない。ルールが実行中に変わって挙動が揺れるのを防ぐための性質でもある。

### 2. ADR 候補

上で出た `Tradeoffs` を「ADR」節の 3 条件にかける。3 条件すべて成立したものだけ `docs/adr/` に書く。1 つでも欠けたら書かない。

### 3. 用語の揺れ

```bash
bash .claude/scripts/glossary-drift.sh <このステージの成果物ディレクトリ>
```

登録済みの避ける別名が使われていれば統一語に直す。あわせて、このステージで新しく定義した語があれば `docs/glossary.md` への登録要否を聞く（新語はスクリプトでは見つからない）。

### 4. 候補がゼロでも1問聞く

候補が 1 つも出なくても「今回、用語集・ADR・ルールに残すことはありますか」を必ず聞く。**「特になし」を AI が推測で選ばない。** ここを省くと記録するかどうかが AI の自己判定に戻り、書かれないまま流れる。候補ゼロは異常ではなく通常の結果。

## memory.md

ステージ実行中に発生した判断を、その都度ためる作業日誌。承認ゲートで中身を見て、残すもの・ルールへ上げるもの・捨てるものに振り分ける。

### 置き場

**ステージごとに 1 ファイル。**

| フェーズ     | 置き場                                               |
| ------------ | ---------------------------------------------------- |
| Inception    | `docs/intents/<slug>/memory/step0.md` 〜 `step4.md`  |
| Construction | `docs/intents/<slug>/units/<unit>/<stage>/memory.md` |

Construction は `explore/` `design/` などステージごとのディレクトリを持つので、その中に置く。Inception は成果物がフラットなので、memory だけ `memory/` にまとめてファイル名でステップを表す。

ファイルはステージ開始時に無ければ作り、既にあれば上書きしない（中断して再開したときに書きためた分を残すため）。承認が済んでも消さない。そのステージの記録として残す。

**ステージをまたいで引き継ぐ用途には使わない。** 未解決の疑問と矛盾は、そのステージを終える前に解消する。持ち越すものは `questions.md` かルールへ上げる。

### 形式

```markdown
## Interpretations

- 2026-08-07T02:14:32Z 曖昧な記述をどう解釈したか; 補足の文脈

## Deviations

- 2026-08-07T03:01:10Z 手順から意図的に外れた点と理由

## Tradeoffs

- 2026-08-07T03:20:44Z 検討した代替案と選んだ理由

## Open questions

- 2026-08-07T04:02:05Z 次回までに確認したいこと
```

- **H2 見出しは上の 4 つに固定する。** ステージ別・日付別の見出しを作らない
- エントリは `- <ISO8601 UTC> <サマリー>; <文脈>`
- 1 行に収まらないときは次行以降にインデントで足す
- タイムスタンプは `date -u +%Y-%m-%dT%H:%M:%SZ` で取る（暗算しない）

**ステージを表すタグは書かない。** ファイルのパスがステージを表すので要らない。見出しは分類（Interpretation / Deviation / Tradeoff / Open question）だけに使い、ステージ名を見出しにしない。

### 書くこと自体に承認は要らない

記録は AI の自動作業。承認を取るのは振り分けの段だけ。

### Open questions の扱い

`Open questions` はルールにも ADR にも上げない。仕様の未確定であって、再利用できる決まりではない。memory.md に残すか、解消したら消す。

## ADR

「ある設計判断を、いつ・何を・なぜ決めたか」を短く残す。コードを見ても「なぜこの形か」は分からず、意図した決定を後から「非効率では」と壊されるのを防ぐ。

### 書くかどうかの判定（3条件すべて成立したときだけ）

1. **後戻りしにくい** — 後で覆すコストが大きい
2. **文脈なしでは驚く** — 将来の読み手が「なぜこうした？」と思う
3. **本物のトレードオフ** — 実在する代替案から理由を持って選んだ

1 つでも欠けたら書かない。この 3 条件が ADR があふれるのを防ぐ核心。「書くコストが低いから念のため残す」で書き始めると重要な決定が埋もれる。

### 置き場・命名

`docs/adr/0001-<slug>.md` の 4 桁連番。`<slug>` は内容を表す kebab-case。番号は使い回さない（deprecated になった番号もそのまま空けておく）。

### 形式

```markdown
# OGP 画像はビルド時に生成し、リクエスト時には作らない

Status: accepted
発生元: og-image-generation

静的サイトとして配信するので、リクエストを受けて画像を作る実行環境が無い。
Satori と Sharp を使い、全記事分をビルド時に書き出す。

却下した代替案: エッジ関数での動的生成 — 実行環境をひとつ増やすことになり、静的配信のままにしておく利点を手放すため。
```

3 行とも必須。

| 行                | 中身                                                                                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Status:`         | `proposed` / `accepted` / `deprecated` / `superseded by ADR-NNNN`                                                                                                |
| `発生元:`         | その判断が出た作業の名前。Inception / Construction を回したなら `docs/intents/<slug>/` の slug、それ以外はその作業名。後から辿れることが目的なので形式は縛らない |
| `却下した代替案:` | 却下した案と理由。判定の3条件目を通った時点で必ず存在する情報                                                                                                    |

本文は 1 段落でよい。タイトルは題目ではなく決定そのものを書く（「画像生成の方式について」ではなく「ビルド時に生成する」）。

### 決定が変わったとき

元の ADR を書き換えない。新しい ADR を書き、元の Status を `superseded by ADR-NNNN` に変え、新しい側から元を参照する。

### 該当する典型

構成の形 / 外部サービスとの連携方式 / 乗り換えにくい技術選定 / 境界・スコープの決定（明示的な「やらない」も含む）/ 素直な道からの意図的な外れ / コードに見えない制約

## 用語集

このリポジトリ固有の語を 1 つに揃えるための、表記を 1 つに決め切る用語集（DDD のユビキタス言語）。同じ概念を別名で呼ぶとユーザーストーリーも設計もぶれるので、先に統一語を決める。

### 置き場

`docs/glossary.md`。個々の作業をまたぐ共有の資産なので `docs/intents/<slug>/` の外に置く。単一の文脈なので 1 ファイルでよい。

### 形式

```markdown
**OGP 画像**（code: ogp-image）
記事ごとにビルド時に書き出す、SNS で共有されたときのカード表示に使う画像。
避ける別名: OG 画像, アイキャッチ, サムネイル
```

日本語の統一語と英語のコード識別子の二層。`避ける別名:` はカンマ区切り。

### 規律

- 統一語を 1 つ選び、残りは「避ける別名」へ落とす。揺れたまま放置すると、語を決めるための用語集が働かない
- 定義は「何であるか」だけを 1〜2 文で。「何をするか」は書かない（振る舞いを書くと仕様と二重管理になってずれる）
- 固有の概念のみ。一般的なプログラミング用語は入れない（一般語が混ざると統一語が埋もれる）
- 用語集であって、仕様・作業メモ・実装の決定の置き場ではない。実装の詳細が混ざり始めたら外れている

### 機械で見つかる範囲

`.claude/scripts/glossary-drift.sh` が検出するのは「登録済みの避ける別名が成果物で使われている」揺れだけ。**新しく出てきた語が未登録であることは検出しない**（日本語の未知語の切り出しは形態素解析なしにはできない）。新語を登録するかどうかは承認ゲートでの人の判断に残る。
